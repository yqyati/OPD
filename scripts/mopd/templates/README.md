# Canonical MOPD Pipeline Templates

These templates are the required starting point for new MOPD launchers. Do not
rebuild the outer control flow from memory.

## Canonical flows

```text
Plain MOPD:
external inputs -> train -> final checkpoint -> merge -> final evaluation

Prefix MOPD:
retained 7k teacher responses -> prefix extraction/merge/validation -> train -> final checkpoint -> merge -> final evaluation

Full-SFT + OPD:
teacher rollout -> full-response SFT -> plain MOPD -> final evaluation
```

The Full-SFT checkpoint is preserved and used to initialize plain MOPD. It is
not evaluated inside the canonical end-to-end pipeline.

## Templates

- `plain_mopd_train_merge_eval.bash.template`
- `prefix_mopd_train_merge_eval.bash.template`
- `rollout_full_sft_plain_mopd_eval.bash.template`

The `.template` files intentionally refuse direct execution. Copy one to a
top-level rjob launcher, remove the template guard, and replace every
`__PLACEHOLDER__` before submission.

The Prefix template requires these additional replacements:

```text
__PREFIX_LENGTH__
__PREFIX_SOURCE_DIR__
__EFFECTIVE_MANIFEST__
```

The generated launcher must read the retained `*_full_response_7168.parquet`
files, extract the requested prefix length, merge the three domains, and
validate the final parquet before invoking training. A pre-existing prefix
parquet is reusable, but teacher rollout is never part of Prefix data
preparation.

## Allowed replacements

Only replace the explicitly named experiment fields:

```text
student model
teacher models
source/prefix/full-response dataset paths
response and model length caps
prefix length and prefix-loss coefficient
batch and mini-batch sizes
learning rate and epochs
expected final step
run/checkpoint/merged-model/evaluation names
GPU allocation
```

Do not rewrite stage ordering, checkpoint publication, merge validation, or
evaluation handoff when creating a parameter variant.

## Mandatory review

Before handing a command to the user:

1. Separate external inputs from outputs generated by this pipeline.
2. Never require a stage output before running that stage.
3. Check zero-output, partial-output, and completed-output states.
4. Compute the final training step from the effective dataset after filtering,
   not the source parquet row count.
5. Require `trainer.save_freq > 0` and require the final actor checkpoint.
6. Require `config.json` and at least one `*.safetensors` after every merge.
7. Keep `train -> checkpoint -> merge -> evaluate` intact.
8. Use the absolute top-level launcher path in `rjob submit`.
9. Run `bash -n` and the non-GPU Hydra config-only path.
10. Never start GPU, Ray, vLLM, training, generation, or evaluation from an
    assistant verification step.
